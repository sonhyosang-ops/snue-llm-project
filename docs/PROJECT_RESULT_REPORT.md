# 교육공무원 인사실무편람 지식도우미 프로젝트 결과 보고서

작성일: 2026-09-27

## 1. 프로젝트 개요

교육공무원 인사실무편람 PDF를 기반으로 학교 업무 질문에 근거 중심으로 답변하는 웹앱을 구축했다.

- 프론트엔드·API: Next.js App Router
- 배포: Vercel
- 인증·데이터베이스·파일 저장소: Supabase
- PDF 파싱·임베딩·답변 생성: Upstage API
- 주요 사용자: 관리자/운영자, 허용된 일반 사용자
- 허용 이메일: `@baegotnuri.es.kr`

## 2. 최종 업무 흐름

1. 사용자가 학교 이메일을 입력한다.
2. Supabase Auth가 로그인 링크를 이메일로 발송한다.
3. 허용 사용자 목록에 등록된 이메일만 접속한다.
4. 사용자는 교육공무원 인사실무편람의 장 버튼을 선택한다.
5. 질문은 선택한 장의 청크와 임베딩을 우선 검색한다.
6. 검색된 공식 문서 근거를 Upstage 모델에 전달한다.
7. 답변의 `[번호]`와 같은 번호의 검색 근거(꼭지·쪽수·원문 일부)가 함께 표시된다.
8. 관리자는 사용자와 PDF 문서를 관리한다.

## 4. 데이터베이스 구조

Supabase PostgreSQL 하나를 사용하며, 장별로 별도 물리 데이터베이스를 만들지 않는다.

- `allowed_users`: 허용 사용자 이메일과 권한
- `profiles`: 사용자 프로필
- `documents`: 업로드 문서와 처리 상태
- `chapters`: 문서의 최상위 장
- `chunks`: 검색 단위 본문 조각
- `embeddings`: 청크 벡터
- `chapter_keywords`: 장별 중요낱말 사전
- `messages`: 질문·답변 기록
- `personnel-pdfs`: 비공개 PDF 저장 버킷

장별 검색은 하나의 데이터베이스 안에서 `chapter_id`로 구분한다. 따라서 데이터 관리가 단순하고, 나중에 여러 문서를 추가하기도 쉽다.

## 5. 파싱 오류와 수정 결과

초기 파싱에서는 목차의 하위 항목까지 장으로 인식하는 문제가 있었다. 예를 들어 `교육법규의 정의와 체계`, `신규 채용` 등이 독립 장 버튼으로 생성되었다.

원인은 목차가 두 칼럼 형태로 추출되면서 `제 N 장`과 장 제목이 여러 줄로 분리되었고, AI가 하위 번호 항목을 최상위 장으로 해석했기 때문이다.

수정 결과:

1. `제 N 장`만 최상위 주제로 인식하도록 프롬프트를 수정했다.
2. 같은 장 번호가 여러 번 감지되면 잘못 저장하지 않고 오류를 발생시키도록 보완했다.
3. 현재 활성 문서의 기존 32개 하위 항목을 8개 최상위 장으로 재구성했다.
4. 기존 1,148개 검색 청크와 임베딩은 유지했다.
5. 장별 중요낱말 사전은 8개 장 기준으로 다시 생성했다.

현재 장 목록:

| 장 | 사용자에게 표시되는 제목 | 쪽수 |
|---|---|---:|
| 제1장 | 교육법과 교원 정원 | 3~20 |
| 제2장 | 교원의 임용 | 21~78 |
| 제3장 | 휴직 및 복직 | 79~216 |
| 제4장 | 복무 | 217~332 |

## 6. Upstage 오류 대응

### 100쪽 초과 오류

571쪽 PDF 전체를 한 번에 전송하지 않고, 최대 100쪽 단위로 나누어 파싱하도록 수정했다. 논리적인 장은 유지하면서 API 요청만 내부적으로 나눈다.

### 임베딩 최대 토큰 초과 오류

임베딩 요청을 작은 청크 묶음으로 제한하고, 한 요청이 4,000토큰을 초과하면 자동으로 다시 나누도록 수정했다.

### 요청 빈도 제한(429)

429 응답과 일시적인 5xx 오류에 대해 대기 후 재시도하도록 추가했다. 단, Upstage 계정의 전체 요청 한도를 초과한 경우에는 일정 시간 대기해야 한다.

## 7. 보안 및 권한

- 서비스용 Supabase 키는 서버 환경변수로만 사용한다.
- 브라우저에는 공개용 Supabase 키만 전달한다.
- Supabase Row Level Security를 활성화했다.
- 관리자 API는 관리자 이메일과 권한을 확인한다.
- PDF 저장 버킷은 비공개로 설정했다.
- 허용 도메인 외 이메일은 로그인할 수 없다.
- 일반 사용자(`user`)와 관리자(`admin`) 역할을 분리해 `/admin` API를 보호한다.
- 비밀키와 API 키는 소스 코드와 결과 보고서에 포함하지 않는다.

## 8. 로그인과 이메일 발송 운영 결과

- Supabase Custom SMTP에 Resend를 연결했다.
- 발신 도메인 `send.muteli.kr`의 검증 상태를 확인했고, 로그인 메일 발송 성공을 확인했다.
- 로그인 링크는 `/auth/callback`으로 이동한다. 확인 창이 세션을 저장하면 최초 로그인 창이 같은 브라우저 안에서 이를 감지해 채팅 화면으로 전환된다.
- 확인 창은 약 1.5초 뒤 자동으로 닫기를 시도하며, 브라우저가 막는 경우 사용자가 직접 닫을 수 있다.
- 가장 최근에 발송된 매직 링크만 사용하고, 링크 만료 또는 사용 후에는 새 링크를 요청해야 한다.

## 12. 운영 시 주의사항

- `localhost:3000`은 개발자 컴퓨터에서만 접속할 수 있다.
- 일반 사용자에게는 Vercel 관리 화면 주소를 안내하지 않는다.
- Supabase 서비스 키와 Upstage API 키를 브라우저, 메신저, 문서에 공개하지 않는다.
- 로그인 요청을 한 브라우저와 메일 링크를 여는 브라우저는 같아야 최초 창의 자동 로그인 전환이 동작한다.
- PDF가 100쪽을 초과해도 시스템 내부 분할 처리가 필요하므로, 업로드 중에는 브라우저를 닫지 않는 것이 안전하다.
- 답변은 문서 기준일 이후 변경된 법령을 자동으로 반영하지 않으므로, 실제 업무 처리 전 최신 공문과 법령을 확인해야 한다.

## 14. `upstage_API` 학습 프로젝트와의 비교

`C:\Users\mutel\Downloads\LLM_Agent_Project\upstage_API`는 Upstage API, PDF 처리, 텍스트 전처리, 임베딩, 요약, Streamlit 사용법을 학습하기 위한 Python 실습 프로젝트다. 최종 웹앱은 이 폴더를 그대로 복사한 것이 아니라, 현재 서비스에 필요한 개념과 처리 방식만 선택해 Next.js·Supabase 구조로 옮겼다.

## 15. Python 코드가 최종 프로젝트에 없는 이유

초기 학습 프로젝트 대부분은 Python으로 작성되어 있지만, 최종 서비스에는 Python 파일을 포함하지 않았다. 이는 Python을 사용할 수 없어서가 아니라, 최종 운영 구조를 Vercel 중심으로 단순화하기 위한 선택이다.

### 최종 기술 선택

현재 구조는 다음과 같다.

```text
브라우저
  → Next.js 화면
  → Next.js Route Handler
  → Supabase / Upstage API
```

Next.js Route Handler는 Vercel Functions로 바로 배포된다. 따라서 PDF 업로드, 인증 확인, Supabase 조회, Upstage 호출을 하나의 TypeScript 프로젝트 안에서 처리할 수 있다.

### Python 백엔드를 별도로 두지 않은 이유

Python을 포함하려면 다음과 같은 별도 운영 요소가 필요하다.

- FastAPI 또는 Flask 서버
- Python 실행 환경과 패키지 설치
- Vercel과 별도 Python 서버 또는 컨테이너 배포
- Next.js와 Python 서버 사이의 API 통신
- 서버별 환경변수·로그·장애 관리
- PDF 임시 파일과 장시간 처리 작업 관리

이 방식은 장기적으로 필요할 수 있지만, 현재 목표인 빠르고 단순한 MVP에는 운영 복잡도와 비용을 추가한다. 특히 Streamlit은 Vercel의 일반적인 Next.js 배포 흐름에 직접 포함되지 않는다.

### Python에서 옮긴 핵심 개념

Python 코드를 그대로 복사하지 않고 다음 개념을 TypeScript로 옮겼다.

- `requests` 또는 OpenAI Python client 호출 방식 → TypeScript `fetch`
- PDF OCR/파싱 함수 → `parsePdf`
- 텍스트 토큰화·불용어·조사 처리 → `tokens`, `normalizeTerm`
- TF-IDF 중요낱말 계산 → `chapterKeywords`
- 임베딩 생성 → `embed`
- 근거 기반 답변 생성 → `answerWithSources`
- 파일 기반 결과 저장 → Supabase Storage·PostgreSQL

따라서 Python 학습 프로젝트의 핵심 지식은 버린 것이 아니라, 운영 환경에 맞는 TypeScript 코드로 재구성한 것이다. 원본 `upstage_API` 폴더는 학습·참고 자료로 보존하고, 최종 서비스 코드에는 현재 요구사항에 필요한 기능만 남겼다.

## 16. 최종 프로젝트와 학습 프로젝트의 역할 구분

| 구분 | `upstage_API` | 최종 `LLM_RAG_PROJECT` |
|---|---|---|
| 목적 | API와 AI 문서 처리 학습 | 실제 사용자를 위한 업무 웹앱 |
| 언어 | Python | TypeScript/Next.js |
| UI | Streamlit | Next.js 웹 UI |
| 저장소 | 로컬 폴더·텍스트 파일 | Supabase PostgreSQL·Storage |
| 인증 | 없음 또는 단순 실행 | Supabase 이메일 인증 및 허용 사용자 |
| 문서 처리 | OCR·요약 실습 | 목차 기반 장 분할·청킹·임베딩·검색 |
| 답변 방식 | 일반 채팅·요약 | 선택 장 범위 내 근거 기반 답변 |
| 배포 | 로컬 Python 실행 | Vercel 운영 배포 |
| 범위 | 여러 AI 기능의 학습 예제 | 교육공무원 인사실무편람 업무 지원 |
