# 핵심 아키텍처 — 장(목차) 선택형 교육공무원 인사실무편람 RAG

이 문서는 **빠르게 구현할 수 있는 첫 번째 웹앱(MVP)** 의 구조를 정의한다.

목표는 허용된 사용자가 로그인한 뒤, 인사실무편람의 장을 선택해 질문하고,
선택한 장의 근거를 바탕으로 답을 받는 것이다.

초기 버전에서는 파인튜닝, 복잡한 자동 토픽 군집화, 물리적인 장별 데이터베이스는 만들지 않는다.

---

## 1. 핵심 원칙

1. **장 하나는 검색 범위 하나다.**
   - 사용자가 선택한 장의 청크만 검색한다.
2. **장별 핵심어 사전은 검색 경로를 확인하는 용도다.**
   - 선택한 장에 질문의 핵심어가 없으면 다른 장의 사전만 확인한다.
3. **다른 장의 본문 검색과 답변은 사용자 동의 후에만 한다.**
4. **답변에는 반드시 PDF 페이지 근거를 표시한다.**
5. **단순하게 시작한다.**
   - 하나의 Supabase 데이터베이스와 몇 개의 테이블만 사용한다.
   - 장별로 실제 데이터베이스를 따로 만들지 않고 `chapter_id`로 구분한다.
   - 파인튜닝 대신 최신 PDF를 다시 색인한다.

---

## 2. 사용자 역할

| 역할 | 할 수 있는 일 |
|---|---|
| 관리자/운영자 | 허용 사용자 등록, PDF 업로드, 장 제목·범위 확인, 문서 활성화/비활성화 |
| 일반 사용자 | 로그인, 장 선택, 질문, 장 변경 제안 수락/거절, 답변·페이지 근거 확인 |

사용자는 다음 두 조건을 모두 만족해야 이용할 수 있다.

```text
1. 이메일이 @baegotnuri.es.kr 도메인이다.
2. 관리자가 미리 등록한 허용 사용자 목록에 있다.
```

도메인만 검사하면 같은 도메인의 모든 계정이 접근할 수 있으므로, 사전 등록 목록도 반드시 확인한다.

관리자는 `allowed_users.role = admin`인 계정만 사용할 수 있다. 기존 관리자 이메일을 다시 등록해도 권한이 일반 사용자(`user`)로 낮아지지 않도록 기존 역할을 유지한다.

---

## 3. 전체 구조

```text
관리자
  │ PDF 업로드
  ▼
Vercel 웹앱
  │
  ├─ Supabase Storage : 원본 PDF 저장
  ├─ Upstage API      : PDF 파싱, 임베딩, 답변 생성
  └─ Supabase DB      : 사용자·장·청크·핵심어·임베딩 저장
                                │
                                ▼
사용자
  │ 로그인 → 장 버튼 선택 → 질문
  ▼
Vercel 웹앱
  │ 선택한 chapter_id로 검색 범위 제한
  ▼
Supabase 검색 결과 + Upstage 답변
  ▼
답변과 번호가 연결된 근거 표시
```

Vercel은 웹 화면과 요청 처리를 담당한다.
PDF 원본은 Supabase Storage에, 검색 데이터는 Supabase Database에 저장한다.

---

## 4. 관리자 PDF 등록 흐름

관리자가 다음 문서를 업로드한다.

```text
2025 교육공무원 인사실무편람(초등·유아).pdf
```

처리 순서는 다음과 같다.

```text
PDF 업로드
  → Supabase Storage에 원본 저장
  → Upstage Document Parse로 페이지·제목·본문 추출
  → 목차와 제목을 기준으로 장 범위 분리
  → 각 장의 본문을 작은 청크로 분할
  → 청크 임베딩 생성
  → 장별 핵심어 사전 생성
  → Supabase에 저장
  → 관리자가 장 제목·페이지 범위를 확인
  → 문서 활성화
```

### 장 분리 기준

목차와 본문의 장 제목을 기준으로 장을 나눈다.

```text
제1장 총칙       1~30쪽
제2장 임용       31~91쪽
제3장 승진       92~143쪽
제4장 복무       144~200쪽
```

Upstage는 PDF의 구조와 텍스트 추출을 돕는다. 실제 장 경계와 청킹 결과는 관리자가 확인·수정할 수 있게 한다.

### 청킹 기준

- 청크는 같은 장 안에서만 만든다.
- 제목과 문단 경계를 우선 존중한다.
- 청크마다 `chapter_id`, 제목, 시작·끝 페이지를 저장한다.
- 한 청크가 다른 장에 걸치지 않게 한다.

---

## 5. 장별 핵심어 사전

각 장에는 별도의 핵심어 사전(Dictionary)을 만든다.

```text
제3장 승진
  승진후보자명부
  경력평정
  근무성적평정
  가산점
  승진임용

제4장 복무
  휴가
  휴직
  육아휴직
  출장
  겸직
```

사전에는 다음 정보를 저장한다.

| 정보 | 설명 |
|---|---|
| term | 정규화된 핵심 낱말 |
| frequency | 해당 장에서의 출현 횟수 |
| score | 해당 장을 대표하는 정도 |
| chapter_id | 어느 장의 사전인지 |

중요어는 단순 출현 빈도만으로 고르지 않는다. `교육`, `교원`, `업무`처럼 모든 장에 흔한 단어를 줄이기 위해,
명사 추출·불용어 제거 후 장별 TF-IDF 점수를 함께 사용한다.

핵심어 사전은 **답변을 만드는 근거가 아니라, 어느 장을 검색할지 판단하는 보조 장치**다.

## 6. 사용자 질문 흐름

### A. 선택한 장에 핵심어가 있는 경우

```text
사용자 선택: 제3장 승진
질문: 승진후보자명부는 어떤 기준으로 작성하나요?
핵심어: 승진후보자명부, 작성기준
```

`승진후보자명부`가 제3장 사전에 있으므로 다음과 같이 처리한다.

```text
제3장 청크만 벡터 검색
  → 관련 근거 청크 선택
  → Upstage에 질문 원문 + 근거 청크 전달
  → 답변 생성
  → 인용 페이지와 함께 표시
```

### B. 선택한 장에 핵심어가 없는 경우

```text
사용자 선택: 제3장 승진
질문: 육아휴직은 최대 몇 년까지 가능한가요?
핵심어: 육아휴직, 휴직기간
```

제3장 사전에 해당 낱말이 없으면, 다른 장의 **핵심어 사전만** 확인한다.

```text
제4장 복무 사전에 “육아휴직” 존재
```

이때 다른 장의 본문을 바로 검색하거나 답변하지 않는다. 먼저 사용자에게 묻는다.

```text
“육아휴직”은 제4장 복무에 포함된 내용으로 보입니다.
제4장 복무에서 검색하여 답변해 드릴까요?

[예] [아니오]
```

사용자가 `예`를 선택한 경우에만 제4장 복무를 검색해 답변한다.

### C. 어느 장의 사전에도 없는 경우

```text
선택한 장과 다른 장에서 관련 핵심어를 찾지 못했습니다.
질문을 더 구체적으로 입력하거나, 다른 장을 선택해 주세요.
```

### D. 로그인 링크 흐름

```text
처음 창: 학교 이메일 입력 → 로그인 링크 발송 대기
메일 링크를 클릭한 확인 창: 로그인 세션 저장 → 로그인 완료 안내 → 자동 닫기 시도
처음 창: 같은 브라우저의 로그인 세션을 감지 → 채팅 화면으로 전환
```

메일 앱이 링크를 다른 브라우저로 여는 경우에는 브라우저별 세션이 분리되므로, 처음 로그인 요청을 한 브라우저와 같은 브라우저에서 링크를 열어야 한다. 이메일 앱이 직접 연 창은 브라우저 정책상 자동 닫기가 막힐 수 있으므로 닫기 버튼을 함께 제공한다.

## 7. 검색과 답변의 역할 분리

```text
핵심어 1~2개
  → 장 선택 확인 및 장 변경 제안용

사용자의 원문 질문 전체
  → 선택된 장 안의 실제 벡터 검색용
```

질문을 핵심어만으로 축약해 답변 검색에 사용하지 않는다.
예를 들어 “승진후보자명부 작성 기준과 경력평정 반영 방법”은 핵심어만 남기면 세부 조건이 사라질 수 있다.

답변은 다음 조건을 모두 만족할 때만 생성한다.

```text
1. 허용된 사용자가 로그인했다.
2. 사용자가 선택했거나, 장 변경을 허락한 chapter_id가 있다.
3. 해당 장에서 충분한 검색 근거를 찾았다.
```

근거가 약하면 답변을 추측하지 않고 “선택한 장에서 확인할 수 없습니다”라고 응답한다.

### 답변 인용 표시

답변 생성에 전달하는 검색 근거는 순서대로 `[1]`, `[2]`처럼 번호를 부여한다. 모델은 사실 문장 뒤에 해당 번호만 붙이고, 화면 하단의 **확인한 근거**도 같은 번호를 표시한다.

```text
답변: 승진후보자명부는 …에 따라 작성합니다. [2]

확인한 근거:
[1] 소제목 · 34~35쪽 · 원문 일부
[2] 승진후보자명부 작성 · 36~38쪽 · 원문 일부
```

따라서 본문의 `[2]`는 하단의 `[2]` 근거 청크와 반드시 대응한다. 페이지 번호만 표시하지 않고 검색에 사용한 원문 일부도 함께 보여 준다.

## 8. 최소 데이터 구조

```text
allowed_users
  email, role, enabled

profiles  (미사용: 초기 설계 잔여, 앱 코드에서 사용하지 않음)
  id, email, role, can_upload

documents
  id, title, year, storage_path, status, is_active

chapters
  id, document_id, chapter_number, title, page_from, page_to, display_order

chunks
  id, document_id, chapter_id, heading, page_from, page_to, content

embeddings
  chunk_id, embedding, embedding_model

chapter_keywords
  id, chapter_id, term, frequency, score

messages
  id, user_id, chapter_id, question, answer, citations, created_at
```

하나의 Supabase 프로젝트와 위 테이블만으로 시작한다.
장마다 데이터베이스나 Storage 버킷을 새로 만들지 않는다.

## 9. 화면 구성

### 관리자 화면

```text
[허용 사용자 관리]
[문서 업로드]
[처리 상태]
[장 제목·페이지 범위 확인]
[장별 핵심어 확인]
[문서 활성화/비활성화]
```

### 사용자 화면

```text
로그인
  ↓
현재 활성 문서 선택
  ↓
[총칙] [임용] [승진] [복무] ...
  ↓
질문 입력
  ↓
답변의 [번호] + 같은 번호의 PDF 근거·원문 일부
```

## 10. MVP에서 하지 않는 일

- LLM 파인튜닝
- 자동 토픽 군집화
- 장마다 독립 데이터베이스 생성
- 여러 PDF를 한 답변에서 자동으로 섞어 검색
- 음성, 이미지, 복잡한 에이전트 기능
- 사용자가 동의하지 않은 다른 장의 본문 검색

이 기능들은 첫 번째 서비스가 안정적으로 동작한 뒤 필요할 때 추가한다.

---

## 11. 구현 순서

1. Supabase Auth와 허용 사용자 목록을 만든다.
2. 관리자 PDF 업로드와 Storage 저장을 만든다.
3. PDF를 목차·장 단위로 분리하고 청크·임베딩·핵심어 사전을 저장한다.
4. 사용자 화면에 장 버튼을 표시한다.
5. 선택한 장 안에서만 검색하고, 근거·페이지를 포함해 답변한다.
6. 다른 장 핵심어 발견 시 장 변경 여부를 묻는다.
7. 처리 오류와 검색 실패를 확인할 수 있는 최소 로그 화면을 추가한다.

첫 구현의 성공 기준은 다음 한 가지다.

> 사용자가 선택한 장에서만 근거를 찾아 답하고, 관련 내용이 다른 장에 있으면 허락을 받은 뒤에만 장을 바꿔 답한다.
