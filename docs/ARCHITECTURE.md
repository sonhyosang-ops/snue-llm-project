# 설계 노트

이 문서는 "왜 이렇게 만들었는가"와 "어디를 만져야 하는가"를 적은 것입니다.
코드 주석이 *무엇*을 설명한다면, 여기서는 *선택*을 설명합니다.

---

## 1. 제약이 설계를 결정했다

| 제약 | 결과 |
|---|---|
| 서버 = 개인 PC 1대, Windows, Docker 없음 | Postgres 대신 SQLite, 컨테이너 대신 `.bat` |
| 사설망 전용, 문서는 외부로 못 나감 | Ollama 로컬 모델 기본, 클라우드 API는 선택 |
| 사용자 소수(현재 1명) | 벡터 검색은 numpy 전수 탐색, 커넥션 1개, 인증 없음 |
| 나중에 확장 가능해야 함 | `providers` / `vectorstore` 추상화, REST API 분리 |

"지금 필요한 최소"와 "나중에 갈아끼울 지점"을 분리한 것이 이 비계의 요지입니다.
FastAPI + REST 를 택한 이유도 같습니다 — 나중에 프런트를 Next.js로 바꾸든
클라우드로 올리든 `/api/*` 계약이 그대로 갑니다. (Streamlit은 이 전환이 불가능합니다.)

## 2. 데이터 흐름

```
PDF
 │  extract.py    텍스트 레이어 추출, 반복 줄(머리말·꼬리말·쪽번호) 제거, 제목 추정
 ▼
페이지 텍스트
 │  chunk.py      문장 경계 존중, 목표 700자 + 겹침 120자, 페이지 번호 유지
 ▼
청크 (검색 단위)
 │  providers.py  bge-m3 임베딩 → L2 정규화 (내적 = 코사인)
 ▼
벡터  ──────────▶ embeddings 테이블 (BLOB) ──▶ vectorstore.py 메모리 적재
 │
 │  topics.py     청크 벡터 평균 = 문서 대표 벡터
 ▼
토픽 배정 ─(기존 분야와 유사)─▶ 배정 + 중심 갱신 + 단어사전 갱신
          └(안 붙음)─────────▶ 보류 → 모이면 군집화 → LLM 명명 → 새 분야
```

질의 시:

```
질문 → 임베딩 → (분야 필터) 벡터 검색 top-k
      → 최고 유사도 < FLOOR ?  ──예──▶ LLM 호출 없이 "확인 불가"
      └─아니오─▶ 폐쇄형 프롬프트 + 근거 → LLM → 인용 번호 검증 → 응답
```

## 3. 핵심 선택 ①: 토픽을 LDA가 아니라 임베딩 군집으로

요구사항 3번("새 PDF에서 새 주제가 생기면 그때 새 데이터셋")이 방식을 결정했습니다.

| | LDA (3주차 강의자료 방식) | 임베딩 + 증분 군집 (채택) |
|---|---|---|
| 문서 추가 | 전체 재학습 필요 | 중심 벡터와 비교만 하면 됨 |
| 토픽 이름 | 단어 분포 → 사람이 해석해야 함 | LLM이 "급식 위생 관리"처럼 명명 |
| 새 토픽 발생 | `num_topics`를 미리 정해야 함 | 임계값 미달 문서가 모이면 자연 발생 |
| 해석·시각화 | 강함 (pyLDAvis) | 약함 → TF-IDF 단어사전으로 보완 |

LDA를 버린 게 아니라 **역할을 나눴습니다**. 분류는 임베딩이, 해석(키워드)은 TF-IDF가 맡습니다.
연구용으로 LDA 비교가 필요하면 `scripts/`에 분석 스크립트를 추가해
같은 청크 집합에 LDA를 돌려 두 분류의 일치도(ARI, NMI)를 재는 방식을 권합니다.
— 이건 그 자체로 논문 한 꼭지가 됩니다.

### 조정해야 할 값

- `TOPIC_ASSIGN_THRESHOLD` (기본 0.62)
  - 높이면 → 분야가 잘게 쪼개짐 (비슷한 매뉴얼이 따로 놂)
  - 낮추면 → 전부 한 덩어리
  - **실제 문서 5~10개를 넣고 눈으로 보며 맞추는 것 말고 방법이 없습니다.**
- `TOPIC_MIN_CLUSTER_SIZE` (기본 2, 단 현재 코드는 `allow_singleton=True`로 문서 1개도 분야가 됨)
  - 학교 매뉴얼은 "문서 1개 = 분야 1개"가 흔해서 이렇게 두었습니다.

### 알려진 한계

- **군집화가 O(n³)** — 문서 수백 개까지는 문제없지만 수천 개면
  `sklearn.cluster.AgglomerativeClustering` 또는 HDBSCAN으로 교체해야 합니다.
- **문서 = 토픽 1개** 가정 — 한 매뉴얼이 여러 분야를 다루면(예: 학교 운영 종합 편람)
  잘못 묶입니다. 개선하려면 *문서* 대신 *섹션* 단위로 토픽을 배정하세요
  (`chunks.topic_id`는 이미 독립 컬럼이라 스키마 변경 없이 가능합니다).
- **LLM 명명이 흔들림** — 같은 군집에 두 번 이름을 지으면 다를 수 있습니다.
  그래서 `POST /api/topics/{id}/rename`으로 사람이 고칠 수 있게 두었습니다.

## 4. 핵심 선택 ②: 할루시네이션 4겹 방어

프로젝트 설명에 적힌 "할루시네이션을 최소화"가 가장 어려운 요구사항입니다.
RAG를 붙인다고 저절로 해결되지 않습니다. 검색이 엉뚱한 걸 가져오면
LLM은 그걸 **근거처럼 보이는 재료**로 삼아 더 그럴듯하게 틀립니다.

| 방어선 | 위치 | 하는 일 |
|---|---|---|
| ① 근거 하한선 | `rag.answer()` | 최고 유사도 < `RETRIEVE_SCORE_FLOOR` → **LLM을 아예 호출하지 않음** |
| ② 폐쇄형 프롬프트 | `rag.SYSTEM_PROMPT` | 근거 밖 지식·추측·"일반적으로" 금지, 모르면 정해진 문장으로 |
| ③ 인용 강제 | 프롬프트 + UI | 사실 문장마다 `[n]`, 화면에서 원문 확인 가능 |
| ④ 인용 검증 | `rag.answer()` | 존재하지 않는 번호를 지어내면 제거하고 경고 표시 |

가장 효과가 큰 것은 **①**입니다. 모델을 부르지 않으면 지어낼 수 없습니다.
다만 하한선이 높으면 답할 수 있는 것도 거절합니다(거절률 ↑).
`RETRIEVE_SCORE_FLOOR`는 정확도와 거절률의 트레이드오프 손잡이입니다.

### 다음 단계로 권하는 것

1. **평가 세트** — 매뉴얼에서 답이 나오는 질문 30개 + 나오지 않는 질문 10개.
   - 답해야 할 때 답했는가 (재현율)
   - 답하면 안 될 때 거절했는가 (**이게 이 시스템의 핵심 지표**)
   - 인용한 쪽이 실제 근거 쪽인가 (인용 정확도)
2. **하이브리드 검색** — `vocab` 테이블이 이미 있으니 BM25를 더해
   "제37조" 같은 고유 표현 질의의 검색 실패를 줄일 수 있습니다.
3. **답변 근거 재확인(self-check)** — 생성된 답을 근거와 함께 다시 LLM에 넣어
   "이 답의 각 문장이 근거에 있는가"를 판정. 비용이 2배지만 규정 안내에서는 값어치가 있습니다.

## 5. 확장 경로

| 상황 | 바꿀 곳 |
|---|---|
| 청크 10만 개 초과 | `config.VECTOR_BACKEND=sqlite-vec` + `SqliteVecStore` 구현 |
| 여러 학교 공동 사용 | SQLite → Postgres + pgvector. `core/db.py` 스키마 거의 그대로 |
| 클라우드 배포 | `app/` 를 Vercel(Next.js) + Supabase 로. `core/` 는 API 서버로 분리 |
| 모델 교체 | `.env` 의 `CHAT_PROVIDER` / `OLLAMA_CHAT_MODEL` 한 줄 |
| 스캔본 PDF | `core/extract.py: ocr_page()` 에 pytesseract 연결 |

추상화를 미리 둔 이유가 이것입니다. 지금은 numpy·SQLite·Ollama지만,
바꿔야 할 때 **호출하는 쪽 코드는 한 줄도 건드리지 않습니다.**

## 6. 열린 질문 (결정 필요)

1. **문서 단위 vs 섹션 단위 토픽** — 종합 편람 같은 문서를 어떻게 다룰지
2. **분야 체계를 사람이 먼저 정할 것인가** — 완전 자동(현재) vs 학교 행정 분류를 시드로 주기
   - 시드를 주면 이름이 안정되지만, 요구사항 3번의 "새 주제 자동 생성"과 절충해야 합니다
3. **거절 문구의 수위** — 지금은 "확인할 수 없습니다"로 끝납니다.
   교직원 입장에서는 "이 문서의 몇 쪽을 보세요" 같은 안내가 더 쓸모 있을 수 있습니다
4. **로그 활용 범위** — `messages` 테이블에 질문·거절 여부가 쌓입니다.
   연구 데이터로 쓸 계획이라면 수집 고지와 개인정보 처리 방침을 먼저 정해야 합니다
